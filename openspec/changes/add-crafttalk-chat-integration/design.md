# Design

## Context

См. proposal.md — Why. Реализация ведётся в репозитории сервиса `uzb-loans-debt-data-collection-service` (UZB-LDDCS) + UI ARM-collection; эта рабочая копия служит planning home, код сервиса здесь отсутствует — tasks сформулированы для выполнения в репозитории сервиса.

Топология: МП ↔ БЗ ↔ CFS ↔ CraftTalk ↔ АРМ Коллектор. CraftTalk автономен, единственная внешняя система для него — АРМ Коллектор (наш сервис). CraftTalk ходит одним API с разными эндпоинтами; логика различается по вызвавшему JS-агенту. В РФ аналогичная интеграция уже работает (референс: QPAY-17297/17378, страница «Интеграция с чат-ботом CraftTalk»); отличия УЗБ — ПИНФЛ вместо номера договора и одно юрлицо.

Действующее REST API v1.1 сервиса менять назад несовместимо нельзя (RESTRICT-06). Код вендора закрыт (RESTRICT-04), вендор в рантайме не участвует.

## Goals / Non-Goals

**Goals:**
- Принять и обслужить вызовы трёх JS-агентов MVP (верификация, обещание оплаты, регистрация контакта) под единым префиксом `/api/craftalk/...`.
- Изолировать будущую смену контрактов вендора в узком слое (контроллеры/DTO), не затрагивая доменную логику.
- Переиспользовать существующие механизмы АРМ Коллектор: результаты работы с заёмщиком («последнее касание», приоритеты колл-листов), расчёт/формирование колл-листов Genesys и рассылок.
- Обеспечить аварийное отключение чата без релиза и обратимо.
- Перенести функционал сегментов из РФ «как есть» (без перепроектирования — решение бизнеса).

**Non-Goals:**
- Операторская модель чата (ролевая модель, статусы/комментарии операторов, закрытие диалогов) — этап 2.
- Push-цепочка CraftTalk → CFS → Messaging Service («тихие часы») — этап 2 (BR-050).
- Агент `send_file` / досудебная претензия — этап 3.
- Кастомная аналитика (ClickHouse/Metabase вендора «из коробки»).
- Сценарии бота (продуктовая группа пишет вручную, уз+рус) и развёртывание CraftTalk/CFS (DevOps).

## Decisions

### D1. Слой API агентов — отдельная группа с адаптером контракта
Новые методы — отдельная версия спецификации (не v1.1). Поскольку точные имена путей и состав параметров приходят от вендора (портал документации, доступ по инвайтам), проектируется фасад: единый префикс `/api/craftalk/...`, семантические имена (`/verify`, `/promise`, `/contact`) как рабочие; финальные пути/поля подгоняются в слое контроллера/DTO без изменений домена.
- Альтернатива: заморозить проектирование до контракта вендора — блокирует все MVP-работы; отклонено.
- Альтернатива: сразу захардкодить предполагаемые пути из РФ-транскрипта — риск расхождения с финальным контрактом; отклонено.

### D2. Верификация: «два запроса, три проверки» на стороне АРМ
Waterfall выполняется в АРМ Коллектор, как в РФ: запрос 1 — проверка «ПИНФЛ + телефон», при неуспехе внутри того же запроса — «телефон как основной активный контакт»; запрос 2 (после ввода клиентом года рождения) — «телефон + год рождения». Полный неуспех — успешный HTTP-ответ с незаполненными параметрами (ERROR-02), чтобы бот вёл сценарную заглушку, а не получал ошибку.
- Альтернатива: три отдельных запроса с оркестрацией в боте — меняет контракт вендора и усложняет сценарий; отклонено (РФ-схема — два запроса).

### D3. RAW-массив — версионируемая DTO (V2)
Состав полей RAW V2 согласуется с аналитиком (TODO). Слоты бота парсят поля, поэтому лишние поля «подрезаем», а не добавляем. В ответе: блок клиента, массив действующих займы (включая просроченные; RESTRICT-05 — только действующие), номер сегмента, ссылка на оплату. Пустой массив займов — валидный исход (нет действующих / клиент не найден однозначно).

### D4. Ссылка на оплату — конфигурируемый шаблон диплинка
Ссылка строится из настраиваемого шаблона (базовый URL диплинка МП + подстановка идентификаторов клиента/займа). Пока команда МП не отдала параметры диплинка (TODO), поле отдаётся из конфигурации и может быть временно пустым — это не влияет на контракт (бот передаёт ссылку как есть).
- Альтернатива: жёстко зашитая ссылка — ломается при смене диплинка; отклонено.

### D5. Сегменты: перенос модели и движка из РФ, страница управления — без перепроектирования
Модель правил (параметры займа/просрочки → номер сегмента, приоритеты) и движок расчёта переносятся из РФ как есть; при `/verify` правила применяются к займам клиента, сегмент кладётся в RAW. Права на страницу — по ролям (состав ролей — TODO, аналитик+бизнес).
- Решение бизнеса: ручное перепроектирование = риск расхождения с проверенной логикой РФ.

### D6. Исключение из каналов — фильтрация на лету по сроку действия обещания
Обещание хранится в АРМ Коллектор (клиент, идентификатор диалога, срок 1–7 дней, дата фиксации, статус). Исключение из колл-листов Genesys и рассылок реализуется фильтром при формировании/обходе списков: клиент с активным обещанием (текущий момент внутри срока) не включается. Автовозврат — следствие истечения срока, отдельная миграция состояния не требуется; фоновая задача ведётся только для актуализации статуса/статистики.
- Альтернатива: синхронизация исключений во внешние системы (Genesys/рассылки) — добавляет хрупкую интеграцию и рассинхронизацию при падениях; отклонено, если формирование колл-листов и рассылок не окажется полностью внешним (см. Open Questions O5).
- Обещание живёт в АРМ: при недоступности CraftTalk исключение и оплата не зависят от чата (BR-020).

### D7. Регистрация контакта — переиспользование логики успешного звонка
Агент «регистрация контакта» передаёт событие активности (семантика событий — TODO вендора). АРМ фиксирует факт эффективного диалога и обновляет «последний успешный контакт» и приоритет телефона в колл-листах тем же кодом, что и успешный звонок. Заход без действий не регистрируется — проверка «эффективности» входит в контракт события.
- Альтернатива: отдельная таблица «чат-контакты» с собственной логикой приоритетов — дублирование и расхождение правил; отклонено.

### D8. Аварийный тогл — флаг в БД + фильтр на пути агентов
Тогл — управляемый флаг в БД (мгновенная согласованность между репликами), проверяемый в общем фильтре/interceptor для `/api/craftalk/**`: включён — все методы отвечают кодом «сервис недоступен» (2). Управление — защищённый админ-эндпоинт/консоль для дежурных/ОПС (механизм и права — TODO DevOps+безопасность), без выпуска релиза, обратимо. Уровень МП (chatLocations) — дочерний эпик МП, здесь не делается.
- Альтернатива: конфиг-файл/фича-флаг сервиса — требует перечитывания конфига или рестарта, не «мгновенно»; отклонено.
- Альтернатива: отключение на уровне CFS/вендора — зависимость от чужой платформы в аварийном сценарии; отклонено (решение о двух уровнях принято бизнесом: наш тогл — первичный и независимый).

### D9. Модель данных и миграции — nullable-first, закладка на этап 2
Новые структуры MVP: правила сегментов, обещания оплаты, факты контактов. Результаты чата в карточке заёмщика читаются из этих таблиц существующими механизмами отображения истории. Схема фактов контактов/результатов закладывается расширяемой (поле «источник результата»: бот/оператор), чтобы этап 2 добавил операторскую фиксацию без ломающей миграции. Миграции — по конвенциям нулевого простоя (новые таблицы, nullable-first).

### D10. Авторизация бота — отдельный service-to-service механизм
Учётная запись бота с секретом хранится на стороне АРМ (аналог роли CHATBOT РФ; механизм не KeyCloak). Боту запрещён UI-доступ на уровне ролей. Конкретный механизм (static secret/mTLS) — согласуется с безопасностью (TODO), контракт — общий фильтр аутентификации для `/api/craftalk/**`.

## Risks / Trade-offs

- [Контракты агентов от вендора неизвестны] → фасад D1 изолирует смену контракта в DTO-слое; до получения контрактов — интеграционные тесты на моке по семантике РФ. Блокер точной спецификации API, не логики.
- [Состав RAW V2 не согласован] → RAW — версионируемая DTO (D3); поля добавляются/убираются без изменения домена. Согласовать до реализации `/verify`.
- [Механизм формирования колл-листов Genesys/рассылок может быть внешним по отношению к АРМ] → тогда фильтр D6 не сработает и потребуется синхронизация. Уточнить на старте реализации (O5) — влияет на объём BACK-030.
- [Пик нагрузки: РФ-ориентир 200–300 одновременных диалогов, verify на каждый] → методы лёгкие (поиск по индексам), но нагрузочное тестирование и индексы под waterfall-поиски заложить в задачи.
- [Секрет бота — ценный доступ к портфелю] → хранение в секрет-хранилище, ротация, запрет UI-доступа; вариант подтвердить с безопасностью (O6).
- [«Дни» обещания 1–7 и сроки — часовой пояс РУз] → считать в Asia/Tashkent, зафиксировать в реализации и тестах.
- [Перенос сегментов «как есть» тащит РФ-специфику] → адаптация стартовых правил под РУз (валюта, параметры займов) — настройка данных, не код; стартовая конфигурация — отдельная задача.

## Migration Plan

1. Миграции БД (новые таблицы: правила сегментов, обещания, факты контактов) — нулевой простой, nullable-first.
2. Деплой сервиса с новой группой `/api/craftalk/...` — методы не доступны снаружи до включения тогла/настройки окружения; v1.1 не изменяется.
3. Настройка учётных данных бота (D10), конфигурация шаблона диплинка оплаты (D4).
4. Включение API агентов (DoD-06: состав настроек — TODO DevOps); деплой UI (страница сегментов, вкладка «Чаты»).
5. Rollback: аварийный тогл (D8) выключает чат без отката релиза; откат релиза безопасен — v1.1 не затронут, данные обещаний/контактов автономны.

## Open Questions

- O1: Точные имена путей, параметры и семантика событий агентов — вендор (портал документации, инвайты). Влияет на DTO-слой, не на домен.
- O2: Состав RAW-массива V2 — аналитик + АРМ Коллектор.
- O3: Параметры платёжного диплинка МП — команда МП (заполнение конфигурации D4).
- O4: Сегмент по умолчанию, когда ни одно правило не совпало (переносится ли поведение РФ; правило из РФ или отдельное) — аналитик.
- O5: Где формируются колл-листы Genesys и списки рассылок относительно АРМ — определяет применимость фильтра D6; если внешнее формирование — добавить синхронизацию.
- O6: Механизм тогла (админ-эндпоинт vs настройка) и права дежурных/ОПС — DevOps + безопасность.
- O7: Состав ролей для страницы сегментов и вкладки «Чаты» — аналитик + бизнес.
- O8: Норматив хранения переписки для РУз — юристы (хранение на стороне CraftTalk, на код АРМ не влияет).
